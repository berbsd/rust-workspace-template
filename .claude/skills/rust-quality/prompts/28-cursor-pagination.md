# Keyset Cursor & Pagination Contract

Verify every list endpoint paginates with the shared `common_types::KeysetCursor<Id>` — not a bespoke cursor struct or hand-rolled base64 — and that the limit contract (`> MAX_LIMIT` → `400`, never silently clamped) holds.

## Why

Keyset pagination is one of the platform's most-repeated shapes: a `created_at` timestamp plus a tie-breaking ID, ordered `(created_at DESC, id DESC)`, encoded as an opaque `base64url(json)` token. `common_types` already owns that shape — the `Cursor` trait (`encode`/`decode`) and the generic `KeysetCursor<Id>` struct. Every service should parameterise that one type with its own typed ID and stop there.

Three failure modes recur when a service re-invents this instead:

1. **Bespoke cursor struct.** A local `struct FooCursor { created_at, id }` with its own `impl Cursor` drifts from the canonical shape — a field rename, a different order, a missing `Copy` — and now cursors are subtly service-specific. It also duplicates code that already exists and is tested once in `common-types`.
2. **Hand-rolled `encode`/`decode`.** Reimplementing the base64url(json) dance per handler is dead weight at best and a wire-format divergence at worst (padding, URL-safe alphabet, JSON field order).
3. **Raw-`Uuid` cursor ID.** `KeysetCursor<Uuid>` compiles, but a raw `Uuid` accepts the nil UUID on decode, where a typed ID (`define_id_type!`) rejects it. Typing the cursor ID costs nothing on the wire (the newtype serialises transparently as the same UUID string) and hardens the decode boundary for free.

Separately, the **limit contract**: `limit > MAX_LIMIT` must return `400 Bad Request` naming the cap — it must **never** be silently clamped down to `MAX_LIMIT`. Silent clamping is a lie to the client (they asked for 200, got 50, with no signal) and it diverges from every service that validates via garde. A leftover imperative `clamp_limit(limit).min(MAX)` helper is the tell.

## Workflow

Scan `services/*/src/**` and `crates/*/src/**`. Skip `target/` and generated code.

### 1. No bespoke cursor structs

Grep for `impl Cursor for` and for structs with the tell-tale pair of fields (`created_at` + `id`) used as a pagination cursor. Any `impl Cursor for LocalStruct {}` where `LocalStruct` is not `KeysetCursor<_>` is a finding — the type should be:

```rust
// feature/<f>/model.rs
pub type FooCursor = KeysetCursor<FooId>;
```

Exception: a list that genuinely cannot sort on `(created_at DESC, id DESC)` — e.g. it orders by a relevance score, a name, or a composite key the generic struct can't express. This is the *only* legitimate reason to deviate, and it must be **reviewed with the user first**. Flag it either way so the deviation is visible; note in the report whether a justifying comment / review reference is present.

### 2. No hand-rolled `encode` / `decode`

Grep for `fn encode_cursor`, `fn decode_cursor`, and manual `URL_SAFE_NO_PAD` / `base64` use inside feature handlers. The canonical calls are `Cursor::encode(&cursor)` and `FooCursor::decode(&s)` (the trait methods). Hand-rolled cursor codecs in a service are findings — delete them and route through the trait.

Bad-cursor decode maps to `400`:

```rust
let cursor = params.cursor.as_deref().map(FooCursor::decode).transpose()
  .map_err(|e| FooError::BadRequest(format!("invalid cursor: {e}")))?;
```

### 3. Cursor ID is a typed platform ID, not raw `Uuid`

**Only applies to a workspace that has a typed-ID system** (`define_id_type!` or
equivalent). This template's own `common-types` doesn't have one — `services/example`'s
`WidgetCursor` is `KeysetCursor<Uuid>` by design, not a finding. Skip this section
entirely for a workspace shaped like that.

Where a workspace does have typed IDs: find every `KeysetCursor<...>`. The type argument must be a `define_id_type!`-generated ID, never `Uuid`. `KeysetCursor<Uuid>` is a finding: introduce (or reuse) the typed ID for that row's PK and parameterise on it. Confirm the wire format is unchanged — the newtype must serialise transparently as the UUID string (it does, if generated by `define_id_type!`), so existing tokens keep decoding.

### 4. Limit is validated, never silently clamped

For each `{Resource}ListParams` (and search-params) struct:

- The `limit` field carries `#[garde(inner(range(min = 1, max = MAX_LIMIT)))]` (or the service's `MAX_*_LIMIT` const), and the **handler actually calls `params.validate()?`** — a garde rule on a struct whose handler never validates is dead code that lets bad limits through.
- The service/repository resolves the effective limit with `params.limit.unwrap_or(DEFAULT_LIMIT)` — it does **not** re-clamp.
- Grep for `clamp`, `.min(MAX`, `enforce_limit_cap`, `clamp_limit`. Any helper that reduces an over-cap limit *instead of rejecting it* is a contract violation — replace it with garde validation at the handler and `unwrap_or(default)` at the service.

Cross-reference: prompt #19 (garde validation coverage) checks the *rule* exists on the field; this check adds that the handler *invokes* validation and that no clamp path bypasses it.

### 5. Constants

`DEFAULT_LIMIT` / `MAX_LIMIT` come from the shared `common-types` constants (or the service's `consts.rs` mirroring the platform values `25` / `50`). Flag any inline `50` / `25` literal in a limit path (this also surfaces under prompt #3, magic numbers — attribute to whichever check the user is running).

## Fixing

For each finding, pick exactly one:

1. **Replace the bespoke cursor** with `pub type FooCursor = KeysetCursor<FooId>;`, delete the local struct and its `impl Cursor`, and re-export at `service::FooCursor` so existing paths resolve.
2. **Delete hand-rolled cursor codecs** and route through `Cursor::{encode,decode}`.
3. **Introduce a typed ID** for the cursor's row PK via `define_id_type!` + `impl_id_sqlx!`, re-export it from `common-types` (or the owning lib crate), and change `KeysetCursor<Uuid>` → `KeysetCursor<FooId>`. Verify wire compatibility with a round-trip test (encode then decode an existing-shaped token).
4. **Activate garde + drop the clamp:** add `params.validate()?` as the handler's first line, keep the `#[garde(inner(range(...)))]` rule, and replace `clamp_limit(params.limit)` with `params.limit.unwrap_or(DEFAULT_LIMIT)` in the service. Delete the clamp helper and any test asserting the old silent-clamp behaviour.

Any deviation from `KeysetCursor` (workflow step 1's exception) must be raised with the user, not applied unilaterally — the common cursor is the default and reviewed deviation is the only escape hatch.

## Verification

```bash
cargo check --workspace --all-targets --all-features
cargo clippy --workspace --no-deps --all-targets --all-features
cargo nextest run --workspace --all-features
```

Prefer a per-service round-trip test proving wire stability after a raw-`Uuid` → typed-ID cursor change: encode a cursor, decode it, assert the ID round-trips. For the limit contract, a test that requests `limit = MAX_LIMIT + 1` and asserts `400 Bad Request` (not a clamped `200 OK`) locks the behaviour in.

## Report format

Group by file. For each finding give file:line, which rule (#1–#5) it violates, and the chosen fix. End with two workspace-level counts: (a) cursors not backed by `KeysetCursor<TypedId>`, and (b) limit paths that clamp instead of reject — those two subsets are the ones that break platform consistency and the client-facing contract respectively.
