# Garde Validation Coverage

Verify every deserialised input — request DTOs, query params, config structs — carries garde rules, and that strongly-typed IDs reject the nil UUID.

## Why

`garde` validates after deserialisation. Without it, a `Json<T>` extractor accepts any structurally-valid JSON and the service trusts the contents. The type system catches *shape* mismatches; garde catches *value* mismatches (empty strings, out-of-range numbers, malformed identifiers).

The most insidious failure mode is the **nil UUID slipping through a strongly-typed ID**. `define_id_type!(UserId, ...)` produces a newtype around `Uuid`, but `Uuid::nil()` (`00000000-0000-0000-0000-000000000000`) deserialises successfully. A handler that takes `Json<CreateThingRequest { owner_id: UserId }>` will happily accept `{"owner_id": "00000000-0000-0000-0000-000000000000"}` unless garde rejects it. Downstream queries then read or write rows scoped to a non-existent user — data leak, data corruption, or both depending on the operation.

## Workflow

Scan all `*.rs` files in `crates/` and `services/`. Skip `target/` and generated code.

### 1. Every `Deserialize` struct also derives `Validate`

Find every `#[derive(...Deserialize...)]` on a `pub struct` (or one used at a deserialisation boundary). Confirm the same derive list contains `garde::Validate` (or `Validate` if imported).

Acceptable exceptions — flag only if the file lacks a comment explaining the choice:

- Internal-only types deserialised from a *trusted* source (e.g. cache snapshots from a private bucket). Comment must say so.
- Types in workspace dependencies whose authors own the validation contract.

Anything else: missing `Validate` derive is a finding.

### 2. Every field carries a `#[garde(...)]` attribute

For each `Validate`-deriving struct:

- Every field must have a `#[garde(...)]` attribute. Silent omission is the bug — garde does not validate fields without rules.
- A field that genuinely has no rule must use `#[garde(skip)]` *with a one-line comment* explaining why.
- Nested struct fields use `#[garde(dive)]` to recurse into the inner struct's validators.

Flag any field with no attribute, and any `#[garde(skip)]` without justification.

### 3. Strongly-typed ID fields reject `Uuid::nil()`

**Only applies to a workspace that has a typed-ID system** (a `define_id_type!`-style
macro generating newtypes like `UserId`/`WidgetId` around `Uuid`, with a matching
`validate_not_nil` garde validator). This template's own `common-types` doesn't have
one — `services/example` takes plain `Uuid` fields directly — so skip this section
entirely for a workspace shaped like that; a bare `Uuid` field is expected, not a finding.

Where a workspace does have one, this is the highest-value check in the file. Find every field whose type is one of the workspace's typed IDs (`UserId`, `WidgetId`, `OrderId`, etc. — anything generated by `define_id_type!`). Confirm the field's `#[garde(...)]` attribute includes a not-nil custom validator:

```rust
#[derive(Debug, Deserialize, Validate)]
pub struct CreateThingRequest {
    /// Widget the thing belongs to.
    #[garde(custom(validate_not_nil))]
    pub widget_id: WidgetId,

    /// Owner — must be a real user.
    #[garde(custom(validate_not_nil))]
    pub owner_id: UserId,

    /// Optional reference; nil means "no parent" by convention.
    #[garde(skip)] // explicitly opting out: nil is the sentinel for "root"
    pub parent_id: Option<ThingId>,

    #[garde(length(min = 1, max = 200))]
    pub name: String,
}
```

The validator lives at `crates/common-types/src/validation.rs` (`common_types::validate_not_nil`); confirm the exact import path against what the existing services use. Don't invent a new validator — flag missing imports and point to the canonical one.

For `Option<TypedId>` fields, the rule still applies when the value is `Some(_)` — garde's custom validator runs against the inner value. Use `#[garde(inner(custom(validate_not_nil)))]` (the `inner` adapter unwraps the `Option`) unless the codebase has an established convention; match what the rest of the workspace does.

For `Vec<TypedId>`: `#[garde(inner(custom(validate_not_nil)))]` validates each element.

### 3.5. Common field types: Email, Phone, URL, Names, Strings

Beyond typed IDs, ensure these high-value fields validate at input boundaries:

**Email addresses** — use a `pattern()` or custom validator. Reject empty strings and obviously malformed addresses:
```rust
#[garde(length(min = 1, max = 254), pattern("^[^@]+@[^@]+\\.[^@]+$"))]
pub email: String,

// Optional email: validate inner if present
#[garde(inner(length(min = 1, max = 254), pattern("^[^@]+@[^@]+\\.[^@]+$")))]
pub backup_email: Option<String>,
```

**Phone numbers** — reject empty strings, enforce reasonable length:
```rust
#[garde(length(min = 10, max = 20))]
pub phone: String,

#[garde(inner(length(min = 10, max = 20)))]
pub alt_phone: Option<String>,
```

**URLs** — if accepting URLs from clients, validate the scheme and reject obviously malformed ones:
```rust
#[garde(length(min = 1, max = 2048), pattern("^https?://"))]
pub webhook_url: String,
```

**Names and user-facing strings** — apply max-length bounds to prevent data corruption and UI overflow:
```rust
#[garde(length(min = 1, max = 100))]
pub name: String,

#[garde(length(min = 0, max = 500))]
pub description: String,

// For optional names/descriptions, use inner
#[garde(inner(length(min = 1, max = 100)))]
pub nickname: Option<String>,
```

**`#[garde(skip)]` is reserved for computed/derived fields only.** Input-bearing fields — anything touched by a user — must validate. Do not use `skip` to silence warnings; add a rule or a one-line comment explaining why the field is exempt (e.g., `#[garde(skip)] // server-computed timestamp`).

### 4. Every handler actually calls `.validate()`

A garde rule on a struct is dead weight if nothing invokes it. For each handler taking a
`Json<T>` or `Query<T>` where `T: Validate`, confirm the handler calls `req.validate(&())?`
(or the stateful form) **before** any service/repository call — not after, not
conditionally, not only in some branches. A handler that extracts a validating type and
never calls `.validate()` is a finding of equal severity to a missing `#[garde(...)]`
attribute — the type having rules and the handler running them are two separate facts, and
both must hold.

### 5. Path / Query parameter types

Handler `Path(...)` and `Query(...)` extractors deserialise into typed values. A
`Query<MyListParams>` struct is a `Deserialize`+`Validate` struct like any other — every
field gets a rule, per section 2 above.

**If this workspace has a typed-ID system** (see section 3's caveat): a `Path<UserId>`
should be backed by a not-nil check somewhere on the boundary — either the typed ID's own
deserialiser rejects nil at the type level, or the handler explicitly checks before
delegating. If the deserialiser already rejects nil, this is redundant for
`Path<TypedId>` and naked-typed-ID extractors, but **not** for fields *inside* request
bodies, where serde calls the underlying `Deserialize` on the inner UUID and the newtype's
invariants don't get a chance to run unless garde fires.

### 6. The OpenAPI bound mirrors the garde bound (drift-guarded)

**Only applies if this workspace documents an OpenAPI surface** (see
`rust-documenter/references/openapi-annotations.md`) — skip entirely otherwise.

A garde bound rejects at runtime but is invisible in the published spec. Every field whose garde rule is length/range/count-bounded should restate that limit in its `utoipa` annotation so the OpenAPI contract advertises the same limit — otherwise the spec under-documents what the service enforces.

- `length(max = N)` → `#[schema(max_length = N)]`; on a `Vec`, `#[schema(max_items = N)]`.
- `range(min = A, max = B)` → `#[param(minimum = A, maximum = B)]` (query) or `#[schema(minimum = A, maximum = B)]` (body).

**Flag** a bounded garde field with no matching `#[schema]`/`#[param]` constraint. Two caveats before flagging:

1. `utoipa` (5.x) accepts only an **integer literal** here — it rejects a `const` path — so when the garde bound is written against a shared constant, the OpenAPI attribute must duplicate the number as a literal. That literal can drift from the constant silently; if this workspace has (or is willing to add) a compile-time assertion macro pairing a constant against a restated literal, use it — otherwise flag the duplication itself as a risk in the report, without inventing a macro that doesn't exist here.
2. A bound with no OpenAPI-expressible form (a count cap over a comma-separated query string, a cross-field rule) can't be a schema/param constraint — it belongs in the `params(...)`/field description, not in this check.

### 7. Cross-references

This check coordinates with — and does not duplicate — two other checks:

- Prompt #13 (error pattern) requires the service error enum to have `Validation(#[from] garde::Report)`. If a struct gains a `Validate` derive and the error enum is missing the variant, prompt #13 catches the gap — not this one.
- Prompt #15 (skeleton consistency) checks that `Config` structs across services follow the same shape. Add findings to #15 if the skeleton drift is the cause; flag here if the shape is right but the rules are missing.

## Fixing

For each finding, pick exactly one:

1. **Add the missing `Validate` derive** and populate every field.
2. **Add the missing field rule.** For typed IDs (if this workspace has them), prefer `validate_not_nil`. For strings, `length(min = N, max = M)` or `pattern("...")`. For numerics, `range(min = ..., max = ...)`. Match the rules already used on analogous fields in the codebase.
3. **Add an explicit `#[garde(skip)]` with a comment** if the field genuinely needs no validation. The comment is mandatory — it forces the reviewer to confirm the choice.
4. **Add the missing `.validate()?` call** at the top of the handler, before any service/repository call.
5. **If this workspace has a typed-ID system, strengthen its macro** so the underlying deserialiser rejects nil at the type level. This eliminates the per-field rule entirely for typed IDs. Coordinate with the macro's owners — touching it changes the contract for every service.
6. **Add the missing OpenAPI bound** (§6, if this workspace documents OpenAPI): restate the garde limit as a `#[schema(...)]`/`#[param(...)]` literal.

Do not silently delete the `Validate` derive to make a warning go away — that's the policy violation Core Principle #7 explicitly forbids.

## Verification

```bash
cargo check --workspace
cargo clippy --workspace --no-deps --all-targets
cargo test --workspace
```

For a richer check, write or extend an existing integration test that POSTs a payload containing `Uuid::nil()` for a typed ID field and asserts the response is `400 Bad Request` with `error_code = "VALIDATION_ERROR"`. One such test per service is enough; the contract is uniform.

## Report format

Group by file. For each finding give file:line, the struct/field name, the rule violated (#1–#4), and the chosen fix. End with a workspace-level summary of typed-ID fields missing `validate_not_nil` — that subset is the security-relevant tail and warrants a separate count.
